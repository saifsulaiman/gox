# GOX v0.2 implementation report

## Outcome

GOX v0.2 provides an analysis-only foundation for whole-program ownership and lifetime inference. It consumes unmodified Go, constructs SSA and a CHA call graph, assigns stable allocation identities, propagates identities through parameters and callers, records container and closure retention, and emits explainable classifications and graphs.

No allocator, runtime, compiler backend, or source-language behavior was changed.

## Delivered capabilities

- Whole-program source-function and method discovery, including closures and test code.
- Static and dynamic call-graph indexing with unresolved-call reporting.
- Stable allocation identities and caller-depth propagation.
- Unique, borrowed, transferred, shared, global, concurrent, and unknown ownership categories.
- Function, caller, region, shared, global, goroutine, channel, external, runtime-managed, and unknown lifetime categories.
- Struct/array/slice/map/append/closure retention analysis and retention-graph SCC cycle detection.
- Conservative handling of closures, goroutines, globals, channels, reflection, unsafe, panic/recover, external SSA boundaries, and recognized FFI.
- Human explanations, step traces, JSON reports, and DOT/JSON graph export.
- Analyzer performance metrics, unit/integration tests, cross-platform CPU accounting, benchmarks, and representative examples.

## Disclaimers

- Classifications are research candidates, not memory-safety proofs.
- The reported potential GC reduction is static site coverage, not expected runtime heap or pause reduction.
- GOX v0.2 does not change allocation behavior and cannot measure application runtime improvements.
- `-closed-world` is valid only when the analyzed executable and all dynamic implementations are genuinely complete.

## Limitations

- CHA is context-insensitive and can introduce false call and return paths.
- The heap graph is allocation-sensitive but not field-, path-, or flow-sensitive enough for code generation.
- Cycle detection covers visible allocation-retention SCCs but not hidden runtime edges or field/path feasibility.
- Goroutine and channel flows lack happens-before, join, and structured-concurrency reasoning.
- Reflection, unsafe, cgo/FFI, plugins, assembly functions, unresolved dynamic calls, and external functions without summaries fall back.
- Exported library APIs are open-world.
- Panic/recover data flow is implicit in SSA and therefore falls back.
- Runtime frequency, allocation size, peak RSS of child tooling, and application-level performance require external profiling.
- Finalizers, weak references, cgo pointer rules, and runtime-internal special objects do not yet have dedicated semantic models.

## Next decision

Run v0.2 against real services, libraries, CLIs, and concurrent workloads. Combine JSON results with Go allocation profiles. Only proceed toward allocation modification if audited results show no unsafe optimistic classifications and meaningful allocation-weighted candidate coverage.
